**The first live import failed on every file.** Fix + regression test.

## What happened

`tabs_index` grew columns in #2 (`collection`, `tags`, …) via `ALTER TABLE`, but the migration ran *after* the whole DDL batch — and that batch ends with

```sql
CREATE INDEX IF NOT EXISTS idx_tabs_index_collection ON tabs_index (collection COLLATE NOCASE);
```

On an existing database `CREATE TABLE IF NOT EXISTS` is a no-op, so the table still had the old columns when the index DDL referenced the new one:

```
error: no such column: collection in
CREATE INDEX IF NOT EXISTS idx_tabs_index_collection ON tabs_index (collection COLLATE NOCASE);
```

Every import file then failed at `indexTab()`. It did not show up in dev because the dev database was created fresh, so the table was born with the columns.

## The fix

Table DDL, then `migrateColumns()`, then index DDL (`CREATE_INDEX_SQL`), so the columns exist before anything references them.

## Proof it is fixed

New test `index - a database from before the library metadata is upgraded, not broken`: it rebuilds `tabs_index` in the pre-#2 shape, inserts a row, then initialises the index.

- against the code as merged (fix reverted, test kept): **FAILED** with exactly the production error, `no such column: collection`
- with the fix: **ok**, 67 passed, `deno check` clean

The test also asserts the old row survives and that `collection`/`tag` filters work straight after the upgrade.

## State on the live instance

The import wrote 1690 tab directories before failing (files + `config.json`, no index rows). They are moved out of `data/tabs` to `quarantine-partial-import-2026-10-06/` (manifest of moved ids inside), so a re-run cannot duplicate them and the boot reconcile cannot index them as orphans. The instance itself is untouched: one tab, the admin account, and the library works — it just logs the index error at boot until this is deployed.
